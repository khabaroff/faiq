# Ingestion Cases

Этот документ фиксирует, какие реальные входы должен принимать `guides/` и как пайплайн должен себя вести в каждом случае.

Цель простая: не спорить заранее про “единственно правильный” формат входа, а покрыть нормальные жизненные сценарии.

---

## Общий принцип

Пайплайн должен быть терпимым к разным способам подачи материала.

На входе может быть:

- одна ссылка
- несколько ссылок
- текст с вкраплёнными ссылками
- markdown-файл
- pdf
- локальный файл
- telegram-ссылка

На первом шаге ingestion не должен пытаться “умно писать статью”.

Его задача только такая:

1. принять вход;
2. понять, что это;
3. разложить на нормализованные `QueueItem`;
4. если не понял — отправить в `needs_review`, а не терять.

---

## Case 1: Один URL в `data/queue/inbox.txt`

### Пример

```text
https://example.com/post-about-agents
```

### Что должно происходить

- ingestion читает строку;
- определяет, что это URL;
- создаёт один `QueueItem`;
- дальше item идёт в обычный pipeline.

### Что считаем успешным

- URL не теряется;
- пустые строки игнорируются;
- одинаковые URL не дублируются в рамках одного запуска.

### Задачки

- Сделать parser для `data/queue/inbox.txt`: одна сущность на строку.
- Игнорировать пустые строки и пробелы по краям.
- Добавить dedupe в рамках одного прохода.
- Добавить тест: один URL -> один `QueueItem`.

---

## Case 2: Несколько URL в `data/queue/inbox.txt`

### Пример

```text
https://example.com/post-1
https://example.com/post-2
https://youtu.be/abc123
https://github.com/user/repo
```

### Что должно происходить

- каждая строка обрабатывается отдельно;
- каждый URL становится отдельным `QueueItem`;
- source type определяется позже или на этапе detect.

### Что считаем успешным

- все валидные строки попали в очередь;
- типы не перепутаны;
- ошибка в одной строке не ломает весь файл.

### Задачки

- Поддержать batch-reading нескольких строк из `inbox.txt`.
- Добавить безопасную обработку битых строк.
- Добавить тест: 4 строки -> 4 item.
- Добавить тест: 3 валидные строки + 1 мусорная -> 3 item + 1 warning.

---

## Case 3: Отдельный текстовый файл с одной ссылкой

### Пример

Файл `data/inbox/2026-05-11-link.txt`

```text
https://example.com/some-article
```

### Что должно происходить

- ingestion видит текстовый файл;
- читает содержимое;
- если внутри одна ссылка и почти нет другого текста, считает это ссылочным input;
- создаёт `QueueItem` для URL, а не для “статьи из txt”.

### Что считаем успешным

- одиночная ссылка не уходит в rewrite как обычный текст;
- источник сохраняет origin, что он пришёл из файла.

### Задачки

- Добавить эвристику: “если в текстовом файле одна ссылка и почти нет текста, это URL source”.
- Зафиксировать порог “почти нет текста” в коде, а не на словах.
- Добавить тест для `.txt` с одной ссылкой.

---

## Case 4: Текстовый или markdown-файл со списком ссылок

### Пример

Файл `data/inbox/links.md`

```markdown
- https://example.com/post-1
- https://example.com/post-2
- https://youtu.be/abc123
```

### Что должно происходить

- ingestion читает файл;
- извлекает из него все ссылки;
- создаёт отдельный `QueueItem` на каждую ссылку;
- сам файл не отправляется в rewrite как статья.

### Что считаем успешным

- ссылки извлечены все;
- порядок можно сохранить, но это не критично;
- файл со списком ссылок работает как удобная “пачка”.

### Задачки

- Сделать extractor URL из `.txt` / `.md`.
- Если файл в основном состоит из списка ссылок, роутить его как batch input.
- Добавить тест для markdown-файла с 3-5 ссылками.

---

## Case 5: Текстовый или markdown-файл с текстом и ссылками

### Пример

```markdown
Надо посмотреть этот подход к extraction.

Ссылка:
https://example.com/post-about-parsing

И ещё заметка: попробовать fallback через markdown endpoint.
```

### Что должно происходить

Здесь есть два возможных режима:

1. если текста мало, а ссылка главная — извлечь URL и обработать как ссылку;
2. если текста много и он сам по себе ценен — сохранить файл как самостоятельный text source.

Для MVP лучше правило попроще:

- если в файле заметно больше текста, чем просто списка ссылок, считать файл самостоятельным source;
- ссылки внутри не терять, но не разбивать автоматически на много item без необходимости.

### Что считаем успешным

- заметка не ломается на куски без причины;
- ссылку внутри всё равно можно найти в `source.md`;
- есть понятное, воспроизводимое правило.

### Задачки

- Зафиксировать heuristic: “список ссылок” vs “самостоятельная заметка”.
- Добавить тест на mixed-content markdown.
- В `meta.json` записывать, что source был `mixed_text_with_links`.

---

## Case 6: Локальный `.md` / `.txt` как самостоятельный source

### Пример

Файл с конспектом, статьёй, заметкой или списком идей.

### Что должно происходить

- ingestion видит, что это не просто контейнер ссылок;
- создаёт `QueueItem` как file source;
- дальше файл идёт в `ARTICLE` flow;
- итогом становится `article.md`.

### Что считаем успешным

- текст не теряется;
- markdown-структура по возможности сохраняется;
- файл не ошибочно превращается в набор URL-задач.

### Задачки

- Разделить “file as source” и “file as queue container”.
- Добавить тест на длинный markdown-файл без ссылок.
- Добавить тест на `.txt` с большим объёмом текста.

---

## Case 7: PDF в `data/inbox/`

### Пример

Файл `paper.pdf`

### Что должно происходить

- ingestion определяет PDF;
- передаёт его в PDF extraction path;
- если текст извлечён, дальше это обычный `ARTICLE` flow;
- если текст не извлёкся, статус `needs_review`.

### Что считаем успешным

- PDF не теряется;
- ошибка extraction не валит весь запуск;
- у неудачных кейсов есть понятный статус.

### Задачки

- Добавить file type detection для `.pdf`.
- Определить extractor и fallback.
- Добавить тест-кейс: PDF с нормальным текстом.
- Добавить тест-кейс: PDF, где extraction ломается.

---

## Case 8: Telegram link в очереди

### Пример

```text
https://t.me/channel_name/123
```

### Что должно происходить

На этапе MVP это пока не “полностью поддержанный Telegram parser”, а специальный URL case.

Значит:

- ingestion принимает ссылку как обычный URL;
- fetch layer пытается понять, можно ли достать raw content;
- если не может, source получает `needs_review`.

### Что считаем успешным

- Telegram link не отбрасывается как мусор;
- проблема фиксируется явно;
- есть место, куда потом подключить отдельный Telegram fetcher.

### Задачки

- Добавить `t.me` в список допустимых URL input.
- Не считать Telegram link ошибкой ingestion.
- В `meta.json` помечать такие кейсы как `telegram_link`.
- Добавить тест: `t.me` URL проходит ingestion без падения.

---

## Case 9: Telegram text/file ingestion позже

### Пример

Это уже не просто ссылка, а реальный вход из бота:

- forwarded text
- attachment
- caption
- media group

### Что должно происходить

Это `v2`, не MVP.

Бот должен:

- принять telegram payload;
- нормализовать его;
- положить либо в `data/queue/inbox.txt`, либо в `data/inbox/`, либо напрямую в `QueueItem`.

### Что считаем успешным

- Telegram не создаёт отдельный “особый пайплайн”;
- он только ещё один способ положить материал в общую систему.

### Задачки

- Не делать это в первой версии.
- Оставить extension point в ingestion model.
- Позже описать отдельным документом `telegram-ingestion.md`.

---

## Case 10: Битый или непонятный input

### Пример

- пустой файл
- бинарный файл неизвестного типа
- строка “посмотреть потом”
- сломанный URL

### Что должно происходить

- ingestion не падает;
- input либо игнорируется, либо получает `needs_review`;
- в логах видно, почему он не был обработан.

### Что считаем успешным

- мусор не валит запуск;
- спорные случаи не теряются молча.

### Задачки

- Добавить safe failure handling.
- Логировать причину пропуска.
- Добавить тесты на пустой, битый и непонятный input.

---

## Минимальные правила для MVP

Вот что нужно поддержать в первой версии обязательно:

1. один URL в `inbox.txt`
2. несколько URL в `inbox.txt`
3. `.txt` / `.md` файл с одной ссылкой
4. `.txt` / `.md` файл со списком ссылок
5. `.txt` / `.md` как самостоятельный текст
6. PDF
7. `t.me` ссылка как допустимый input
8. safe handling для мусора

---

## Что важно проверить руками

Кроме юнит-тестов, нужны реальные прогоны на живых примерах:

- обычная статья
- длинный пост
- список ссылок в markdown
- заметка с текстом и одной ссылкой
- YouTube URL
- GitHub repo URL
- Telegram URL
- PDF

## Итог

Идея простая:

мы не заставляем пользователя “правильно подавать” материал одним способом.

Мы делаем ingestion достаточно гибким, чтобы он:

- принимал разные разумные входы;
- не терял материал;
- не ломал запуск на мусоре;
- приводил всё к понятному набору `QueueItem`.

А уже потом основной pipeline решает, как это fetch/process/store.
